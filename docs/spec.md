# Tender Tracker: AmanaDB showcase app (implementation spec)

Audience: coding agent working in the VS Code workspace.
Purpose: a small, ordinary-looking Web2 app whose **only database is AmanaDB**, to show that a developer can get tamper-evident, audited storage without touching Fabric.

## 1. Goal and non-goals

**Goal.** Show that a Web2 developer can build a public-procurement tracker with Next.js, the AmanaDB SDK and one project credential, and get versioning, per-collection audit logs, soft delete and tamper-evidence without writing any blockchain code.

**Non-goals.**
- No Fabric-specific code in the app. It uses the SDK only. If something needs Fabric knowledge, that is a gap in AmanaDB: log it in `GAPS.md` and do not work around it.
- No second database. No SQLite, Postgres, Redis or any other data store. Users, roles and all domain data live in AmanaDB.
- Not a full e-procurement system (no payments, supplier registration workflow or document management).
- No new AmanaDB features. If the current API cannot do something below, note it in `GAPS.md` and use the closest supported behaviour.

## 2. Actors

| Actor | Role in app | AmanaDB mapping |
|---|---|---|
| Procuring entity (PE) admin | Publishes tenders, opens bids, records award | App role `pe_admin`; the project owner developer issues the app's project credential |
| Evaluation committee member | Records scores | App role `evaluator`; writes through the project credential |
| Bidder | Submits sealed bid | App role `bidder` |
| Oversight/auditor | Reads everything, views audit log | App role `auditor`; read-only views |
| Public | Views published tenders and awards | Unauthenticated read-only pages |

App users are **not** Fabric identities. The app authenticates to AmanaDB with the project credential, and app users are records in a `users` collection. Per-user attribution is done by writing the app user id into record data. This limitation must be stated in the README.

## 3. Collections and record shapes

All record keys are auto-generated by AmanaDB. `data` is JSON.

1. **users**: `{ email, name, role, passwordHash, active, createdAt }`. `passwordHash` is a salted scrypt hash (Node `crypto.scrypt`), never a plain password. Deactivating a user uses soft delete.
2. **tenders**: `{ title, description, entity, category, budgetCeiling, openDate, closeDate, status: DRAFT|PUBLISHED|CLOSED|AWARDED|CANCELLED, docHash? }`
3. **bids**: `{ tenderId, bidderId, commitment, submittedAt }`. `commitment` is `sha256(canonicalJson({amount, docHash, salt}))`. Nothing else about the bid is stored at submission time.
4. **bid_reveals**: `{ bidId, tenderId, amount, docHash, salt, revealedAt, verified: bool }`. Written at bid opening. `verified` is computed by recomputing the commitment.
5. **evaluations**: `{ tenderId, bidId, evaluatorId, criteria: [{name, score, comment}], total }`. Amended via update (version increments).
6. **awards**: `{ tenderId, winningBidId, justification, decidedBy, decidedAt }`.
7. **complaints** (stretch): `{ tenderId, filedBy, text, status }`.

Uploaded documents stay off-chain, as files on the server's disk (`storage/documents/`), and only their SHA-256 goes into AmanaDB. This is file storage, not a database.

**Sensitive collection.** `users` holds password hashes. It must never be returned by any public route, and the audit log page must not list it (or must redact its data). Record this in the README as a deliberate rule and log in `GAPS.md` whether AmanaDB can restrict reads on one collection differently from the rest.

## 4. Feature-to-demo mapping

| AmanaDB feature | Where it shows up |
|---|---|
| Versioning + optimistic concurrency | Two evaluators editing the same evaluation; the loser gets a clear version-conflict message |
| Per-collection audit log | "History" view per collection: who did what and when (evaluations and awards are the key ones) |
| Soft delete | Cancelling a tender, withdrawing a bid or deactivating a user keeps full history |
| Tamper-evidence | Commit-reveal check on bids; a tampered reveal or altered document is flagged |
| Reader/writer roles | Public and auditor views are read-only; write routes require the right app role and a writer role on the credential |
| Project credential | The app starts with one credential from server environment config; no identity code in the app |

## 5. Core flows (build in this order)

1. **Sign up and sign in.** Sign-up creates a `users` record with role `bidder`. Sign-in looks the user up in AmanaDB, verifies the password hash, and issues a signed, encrypted session cookie (no server-side session store). Staff accounts (`pe_admin`, `evaluator`, `auditor`) are created by the seed script.
2. **Publish tender** (PE admin). Create in `tenders` with status PUBLISHED. The public page lists it.
3. **Submit sealed bid** (bidder). The commitment is computed **in the browser** with Web Crypto, so the amount and salt never reach the server at this stage. The server stores only the commitment. The bidder gets a receipt (bid id, commitment, and a downloadable file with the amount, document hash and salt, which they must keep). Reject after `closeDate`.
4. **Open bids** (PE admin, only after `closeDate`). Each bidder submits their reveal data from the receipt. The server recomputes the commitment, and writes `bid_reveals` with `verified` true or false. Mismatches are flagged clearly.
5. **Evaluate** (committee). Create and amend evaluations. Version conflicts are shown to the user (reload latest, copy own changes); never overwritten silently.
6. **Award** (PE admin). Write `awards`, set the tender status to AWARDED.
7. **Public verification page** for any tender: full timeline (published, bids received, opened, evaluated, awarded) rebuilt from records plus the collection audit logs.
8. **Tamper demo** (`scripts/tamper-demo`): edits an uploaded document on disk and shows the verification page flagging the hash mismatch, while the AmanaDB record remains unchanged.

## 6. Tech choices

- **Framework:** Next.js (App Router) with TypeScript, using Server Components, Server Actions and Route Handlers. Node runtime only for anything that calls AmanaDB (not the Edge runtime).
- **AmanaDB access:** `@amanadb/sdk`, imported only in `src/services/amanadb.ts`, which starts with `import "server-only"`. No client component may import the SDK, the project credential, or anything that reads it.
- **Sessions:** signed, encrypted cookie (iron-session, or Auth.js with the credentials provider and the JWT strategy). No session table.
- **Authorization:** check role in every Server Action and Route Handler, not only in middleware.
- **Caching:** the verification page and any page showing bid or evaluation state must be dynamic (`dynamic = "force-dynamic"` or `cache: "no-store"`), because a cached "verified" result would defeat the demo. The public tender list may use short revalidation.
- **Commitment code:** `src/lib/commitment.ts` (canonical JSON plus SHA-256 via Web Crypto) is shared by the browser (submit) and the server (open and verify), so both produce identical output.
- **Styling:** driven by the design tokens in `src/styles/tokens.css` (see the design brief).
- **Config:** `.env.local` with the AmanaDB gateway URL, the project credential or wallet path, and the session secret. None of these are ever exposed to the client (no `NEXT_PUBLIC_` prefix).

## 8. Acceptance criteria

- A fresh developer can run the app against a running AmanaDB with only the gateway URL, the project credential and a session secret.
- The repository contains no other database: no SQLite files, ORM, or database dependency in `package.json`.
- All domain and user data is read and written through the SDK wrapper, server-side only.
- The SDK and credential never appear in client bundles.
- Version conflict on evaluations is surfaced, never overwritten silently.
- Bid opening before `closeDate` is rejected; a bid whose reveal does not match its commitment is flagged.
- Cancelled tenders, withdrawn bids and deactivated users remain visible in audit history.
- Password hashes are not returned by any public route or shown in the audit log page.
- The tamper demo shows detection.
- The README explains the app-user vs Fabric-identity limitation and lists the `GAPS.md` findings.

## 9. Open items to verify against the current AmanaDB build (do not assume)

1. Exact SDK method names, project-credential setup, and how writer and reader roles are enforced when the app uses one project credential.
2. **Lookup by field.** Sign-in needs to find a user by email, but record keys are auto-generated. Check whether the SDK supports lookup by a field or a caller-chosen key. If not, the fallback is to list the `users` collection (paginated) and filter on the server, which is acceptable for a demo but must be recorded in `GAPS.md` as a limitation for real use.
3. Whether the per-collection audit log returns actor identity and record keys in a form usable for the timeline, and whether it can exclude or redact the `users` collection.
4. Whether reads on one collection (users) can be restricted differently from the others.
5. Pagination behaviour of collection listing for the public tender page.
6. SDK language: the original concept note said PHP or Python clients, and the current SDK is TypeScript. This spec assumes TypeScript because of Next.js. Confirm before locking the stack.
